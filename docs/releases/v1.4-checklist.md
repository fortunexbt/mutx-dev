# v1.4 Release Checklist

This checklist is the fail-closed bar for MUTX v1.4.

Historical outcome: v1.4.0 was published without the five-file desktop artifact set. The desktop
checks below were not satisfied for a v1.4.0 binary release, and this checklist must not be treated as
evidence that v1.4.0 DMGs or ZIPs exist. The public download lane fails closed or selects the newest
older release that satisfies the complete artifact and checksum-manifest contract.

## Positioning Rule

Promote `app.mutx.dev/dashboard` to **Supported** only when all checks above pass on the release candidate machine, including signed packaging, notarization, checksum publication, and launch validation.

Keep `app.mutx.dev/control/*` and preview or redirect-backed dashboard routes labeled **Preview** and out of the primary stable navigation until their live contracts are complete.

## Launch Order

1. Confirm the notarized macOS assets exist on the `v1.4.0` GitHub release; if they do not, do not
   identify v1.4.0 as a desktop release or advertise architecture download links for it.
2. Confirm `docs/releases/v1.4.md` is merged, `https://mutx.dev/docs/releases/v1.4` is live, and `https://mutx.dev/releases` reflects the same release.
3. Verify RBAC enforcement on `/audit/*`, `/security/*`, `/policies/*`, `/approvals/*` routes.
4. Verify OIDC token validation with configured IdP (optional — skip if no external IdP).
5. Run `helm lint infrastructure/helm/mutx/` and `helm template` to validate the chart.
6. Run the Railway production-promotion workflow for the frontend and backend services.
7. Run `bash scripts/verify-production-release.sh`.
8. Verify the public download, release, auth, dashboard, API, docs, and Kubernetes surfaces point to the supported v1.4 surfaces.

## New Environment Variables

The v1.4 release introduces these optional environment variables:

```
# OIDC Token Validation (optional — enable when connecting an external IdP)
OIDC_ISSUER=
OIDC_CLIENT_ID=
OIDC_JWKS_URI=

# CrewAI Adapter (required if using run_crew())
MUTX_API_KEY=***
```

## Breaking Changes

- **RBAC is now enforced.** Update test fixtures or service accounts that relied on open access to `/audit/*`, `/security/*`, `/policies/*`, `/approvals/*` with appropriate roles.
- **CrewAI `run_crew()`** no longer accepts an empty API key. Set `MUTX_API_KEY` or pass `api_key` explicitly.

## Railway Secrets Contract

The production-promotion workflow expects:

- `RAILWAY_TOKEN`
- `RAILWAY_PROJECT_ID`
- `RAILWAY_FRONTEND_SERVICE_ID`
- `RAILWAY_API_SERVICE_ID`
- `RAILWAY_ENVIRONMENT_ID`

Optional overrides:

- `site_url`
- `app_url`
- `api_url`
- `docs_release_url`
- `release_identity_url`

Direct manual promotion requires `confirm_production` to equal `PROMOTE <release-tag>`. The public
`/mutx-release.json` identity must then match the exact tag, package version, and full commit SHA.

## Release Trust Prerequisites

Before creating a release tag or running `.github/workflows/release.yml`:

- Enable GitHub immutable releases for the repository. Publication follows the required
  draft → attach assets → verify → publish sequence; the workflow then requires GitHub's immutable
  release attestation.
- Configure tag rules for `v*`, `cli-v*`, and `sdk-v*` that restrict tag creation, update, and
  deletion to release maintainers. Each release ref must be an annotated, cryptographically signed
  tag that GitHub reports as `verified` with reason `valid`.
- Create the tag only on a commit already reachable from `origin/main`. The peeled tag commit,
  workflow event ref/SHA, and the relevant `package.json` or `pyproject.toml` version must agree.
- Create a GitHub Environment named `release-publishing`, enable required reviewers, prevent
  self-review where policy requires it, and scope these secrets to that environment:
  `APPLE_DEVELOPER_ID_APP_CERT_B64`, `APPLE_DEVELOPER_ID_APP_CERT_PASSWORD`, `APPLE_API_KEY_B64`,
  `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`, `APPLE_TEAM_ID`, `APPLE_KEYCHAIN_PASSWORD`,
  `PYPI_API_TOKEN`, and `HOMEBREW_TAP_TOKEN`. `APPLE_TEAM_ID` is also used to verify the signer
  identity during recovery.
- Keep Railway credentials only in the required-reviewer `production` Environment used by the
  reusable promotion workflow; do not duplicate them as repository or organization secrets, and do
  not pass inherited secrets from the caller. Repository-level release jobs need only
  `contents: read`, except the publication jobs that receive `contents: write`.

The workflow serializes runs per exact tag. For recovery of an already-published immutable stable
release, dispatch with `operation=promote_existing`, the exact `vX.Y.Z` tag, and
`confirm_production=PROMOTE vX.Y.Z`. Recovery does not rebuild, upload, edit, or republish assets.
It requires `gh release verify`, verifies every local asset against its release attestation, checks
the exact checksum manifest and streamed digests, validates code signatures/notarization and Apple
Team ID, and only then enters the protected production promotion. Promotion compares both live
release identities immediately before Railway deployment, rejects downgrades, and permits an exact
same-version recovery.

## Desktop Support Floor

Any desktop package produced from the v1.4 source line must use Electron `43.2.0` and set
`build.mac.minimumSystemVersion` to `12.0`. Its support floor would be macOS 12 Monterey for both
Apple silicon and Intel; Catalina and Big Sur are not supported by this Electron line. No v1.4.0
desktop artifact set was published, so this source configuration is a candidate requirement, not
evidence about a shipped v1.4.0 binary.

## Helm Values Contract

Three value overlays are available:

| Overlay | File | Use case |
| --- | --- | --- |
| Dev | `values.yaml` | Single replica, minimal resources, managed DB enabled |
| Staging | `values.staging.yaml` | Middle ground — moderate replicas, reduced resources |
| Production | `values.prod.yaml` | HA replicas, topology spread, PDBs, managed DB disabled |
